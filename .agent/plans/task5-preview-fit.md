# Task 5：预览画面被裁切，要求「显示完整」

> 需求原文：摄像头预览位图与检测框的 view 显示的图像有剪裁 不能显示完整 调整能显示完整

## 1. 现象与根因

### 1.1 根因（显示侧，主因）

`CameraFrameView.onDraw`（`app/src/main/java/com/openthinks/onnx/example/CameraFrameView.java:110-120`）当前是
「铺满优先 + 裁切上限」策略（Task 4 更新点 1 引入）：

```java
float fitScale  = Math.min(getWidth() / cw, getHeight() / ch);   // 完整显示（等比，可能留黑边）
float fillScale = Math.max(getWidth() / cw, getHeight() / ch);   // 铺满（必然裁掉一边）
// 优先铺满（宽度方向铺满、垂直居中裁切），但裁切不超过 MAX_CROP_FACTOR 倍
float s = Math.min(fillScale, fitScale * MAX_CROP_FACTOR);       // MAX_CROP_FACTOR = 1.4f
```

手机竖屏时 `fillScale` 适用（宽度铺满），画面按**垂直居中裁切**绘制，上下各裁掉一部分。
这就是"显示的图像有剪裁、不能显示完整"的直接原因——**画面本身没变，是绘制时被裁掉了**（检测框同步被裁，两者仍对齐）。

### 1.2 量化（帧 720x1280 竖屏，预览区取屏高 60%）

| 设备 | 预览区 | fit 缩放 | fill 缩放 | 采用 s | 绘制尺寸 | 裁切比例 | 黑边 |
|---|---|---|---|---|---|---|---|
| 1080x2340 | 1080x1404 | 1.097 | 1.500 | **1.500** | 1080x1920 | **垂直裁 26.9% 帧高** | 无 |
| 1080x2400 | 1080x1440 | 1.125 | 1.500 | **1.500** | 1080x1920 | **垂直裁 25.0%** | 无 |
| 1440x3120 | 1440x1872 | 1.462 | 2.000 | **2.000** | 1440x2560 | **垂直裁 26.9%** | 无 |
| 1280x800（平板横屏） | 1280x480 | 0.375 | 1.778 | 0.525 | 378x672 | **裁 28.6%** | 左右各 451px |
| 2560x1600（平板） | 2560x960 | 0.750 | 3.556 | 1.050 | 756x1344 | **裁 28.6%** | 左右各 902px |

两点结论：

1. 手机竖屏：**约 1/4 的帧高（上下各约 1/8）看不到**，且没有任何黑边提示"画面被裁了"。
2. 宽屏/平板：因为 1.4 倍上限先被触发，缩放取到中间值 → **既裁掉 28.6% 又留黑边**，是"两头不讨好"的组合。

### 1.3 采集侧的可能性（次要，需确认是否也算问题）

当前采集分辨率是 1280x720（16:9），而传感器原生多为 4:3 —— 16:9 流本身只用到了 sensor 的一部分视野。
如果需求指的是"视野太窄"（而不是"绘制被裁"），那是采集侧问题，需要改流分辨率（见第 4 节方案 D）。
**如何区分**：截图后若画面**上下被裁且无黑边** → 1.1 的绘制裁切（主因）；若画面**上下有黑边、视野仍偏窄** → 采集侧 16:9。

## 2. 方案对比

### 方案 A（推荐，最小改动）：恢复等比完整显示

`MAX_CROP_FACTOR` 由 `1.4f` 改为 `1.0f` —— 公式退化为 `s = fitScale`，即**永远不裁切**。
保留该常量与公式结构，语义注释写清「1.0 = 完整显示（不裁切）；>1.0 = 允许裁切换铺满」，以后想切回一个数字即可。

| 设备 | 预览区 | s=fit | 绘制尺寸 | 黑边 | 画面宽/屏宽 |
|---|---|---|---|---|---|
| 1080x2340 | 1080x1404 | 1.097 | 790x1404 | 左右各 145px | 73% |
| 1080x2400 | 1080x1440 | 1.125 | 810x1440 | 左右各 135px | 75% |
| 1440x3120 | 1440x1872 | 1.462 | 1053x1872 | 左右各 194px | 73% |
| 2560x1600 | 2560x960 | 0.750 | 540x960 | 左右各 1010px | 21% |

- 代价：左右出现黑边，画面宽度占屏宽 73%~75%（手机）；这正是 Task 4 更新点 1 想要消除的东西 ——
  **「完整」与「铺满」互斥**，本方案按 Task 5 的优先级选「完整」。
- 平板横屏本来画面就小（21% 屏宽），与本次改动无关（预览区只占屏高 60% + 帧是竖长条）。

### 方案 A+（推荐叠加，可选）：把预览区高度占比 60% → 70%，减小黑边

`activity_main.xml` 预览区 `layout_weight` 3 → 7，日志区 2 → 3（预览 70% / 日志 30% 屏高）。

| 设备 | 高度 60%（现状） | 高度 70% | 日志区 |
|---|---|---|---|
| 1080x2340 | 绘制宽 790px（73% 屏宽），黑边 145px | 绘制宽 921px（**85%**），黑边 **79px** | 40% → 30% 屏高（约 700px，可显示 40+ 行日志） |
| 1440x3120 | 绘制宽 1053px（73%），黑边 194px | 绘制宽 1228px（**85%**），黑边 **106px** | 936px |

- 效果：画面更大、黑边减半，代价是日志区从 40% 降到 30% 屏高。

### 方案 B：预览区高度按帧比例自适应（完整 + 铺满宽度 + 零黑边）

高度 = 屏宽 × 1280/720 = 屏宽 × 1.778。

- 手机竖屏：预览高需 82% 屏高 → 日志区 + 按钮栏只剩 18%（约 420px）→ **日志区过矮**，与 Task 4 的诉求冲突。
- 平板横屏：需要 284% 屏高 → **完全不可行**。

结论：不推荐（除非日志区可以接受被压到 18%，或干脆去掉日志区）。

### 方案 C：预览框固定比例 + 点击切换「完整/铺满」

方案 A 为默认，长按（或点击）预览在 fit/fill 间切换，状态栏提示当前模式。
好处：两种诉求都能满足；代价：新增交互与一个 `PreviewScaleMode` 状态，属于增强项（需确认是否要）。

### 方案 D：采集侧改 4:3 以获得更大视野（仅在 1.3 成立时才需要）

在 `CameraController` 选择分辨率时优先 4:3（如 1280x960 / 960x720），预览与检测的视野都会变宽。
代价：letterbox 几何、检测框映射都要跟着重新验证（现有 4 张 val 图的 IoU 用例仍有效，但真机视野变化需复核）；
且帧更高，纯 CPU 的 YUV→RGB 与推理前处理开销略增。**不建议在没有明确需求时做。**

## 3. 推荐

**方案 A + A+**：`MAX_CROP_FACTOR = 1.0f`（保证绝不裁切）+ 预览区高度 60% → 70%（把黑边压到最小）。

## 5. 验证方式（视觉项）

1. 真机截图后按像素自检：取预览区最左/最右两列与最上/最下两行，若为纯黑或纯背景色即为黑边；
   黑边宽度应与上表算式一致（1080 宽屏、70% 高度时约 79px）。
2. 关键对齐检查：**框必须仍与画面里的物体对齐**（同一个 `contentRect` 映射，不裁切后更易观察）。
3. 顺带确认日志区在 30% 屏高下可正常滚动、行内容完整（Task 4 更新点 2 的成果不回退）。
